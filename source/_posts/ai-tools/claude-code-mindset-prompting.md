# 怎么给 Claude Code 下指令：Prompt 技巧实战

有一次我让 Claude Code "优化一下配置文件"，它把 `_config.yml` 和 `_config.butterfly.yml` 全部重写了——格式改了、注释删了、主题配色也换了。本地预览一看，整站样式崩掉。回滚之后我反思了很久：这个翻车的根因不是 Claude 能力不行，是我给的任务太模糊。

<!-- more -->

核心认知只有一句话：**跟 Claude Code 对话不是聊天，是给 Agent 下任务**。聊天可以含糊，任务必须清晰。掌握了这个心智模型，剩下的就是技术问题。

---

## 四个核心原则

### 原则 1：说目标，不说步骤

Claude 是有判断力的执行者，不是只会按指令运转的机器。告诉它"我要什么"，比告诉它"怎么做"效果好得多。

**Before**：

> 先读一下 main.go，然后看一下 router 目录，找到 /api/users 这个路由，把它的 handler 改成从数据库查询而不是返回硬编码数据，然后运行测试，如果测试通过就提交。

**After**：

> `/api/users` 路由目前返回硬编码数据，改成从数据库查询。确保现有测试通过后再提交。

正例更短，但信息更清晰。Claude 自己会去读文件、找路由、改代码、跑测试——这些步骤不需要你手把手教。

### 原则 2：加约束，不只是加描述

光说"改好一点"等于没说。要明确什么叫"好"。

**Before**：

> 把这个函数优化一下。

**After**：

> 优化 `internal/service/user.go` 的 `ListUsers` 函数，要求：
> 1. 时间复杂度降到 O(n) 以下
> 2. 不改变函数签名
> 3. 保留现有测试

三个约束（性能目标、接口不变、测试兼容）比一句"优化"有用得多。

### 原则 3：给参考，不要从零开始

如果你心里有一个想要的效果，直接给 Claude 一个参考文件，比用文字描述快 10 倍。

**Before**：

> 写一个错误处理的中间件，要求能捕获 panic，返回 JSON 格式的错误响应，并且记录日志。

**After**：

> 参考 `internal/middleware/auth.go` 的风格，写一个错误处理中间件。要求：捕获 panic、返回 JSON 错误响应、记录日志。

"参考 `auth.go` 的风格"这几个字，省去了关于命名规范、包结构、错误码格式的一大堆描述。

### 原则 4：复杂任务要拆分

一个大的 prompt 不如三个小的 prompt。不是因为 Claude 处理不了长文本，而是分步执行可以让你在每一步检查结果、调整方向。

以"重构用户模块"为例，拆成三步：

```bash
# 第一步：只分析，不改代码
> 看一下 internal/service/user.go，当前 800 行。
> 列出你认为应该拆分的方法和拆分方案，不要改代码。

# 第二步：确认后只改模型层
> 按上一步的方案，把认证方法提取到 auth.go。
> 只改模型层，不动 API，确保编译通过。

# 第三步：模型改完后更新上层
> 基于 new model 更新 API 层和测试。确保所有测试通过。
```

## 原则速查表

四张表帮你快速对照，写 prompt 之前扫一眼就够了。

| 原则 | 本能写法 | 应该怎么写 | 关键收益 |
|---|---|---|---|
| 说目标不说步骤 | "先读文件 A，再看文件 B，找到函数 C，改成 D" | "函数 C 当前行为是 X，改成 Y" | Claude 自行规划路径，避免遗漏 |
| 加约束不加描述 | "优化一下" | "优化，不改签名，测试全过" | 明确边界，防止过度修改 |
| 给参考不从零开始 | "写一个中间件，捕获 panic，返回 JSON" | "参考 auth.go 风格，写错误处理中间件" | 自动继承代码风格和项目约定 |
| 拆分复杂任务 | "重构整个用户模块" | 先分析 → 再改模型 → 最后改 API | 每步可检查，方向可调整 |

## 进阶技巧：让 prompt 更精准

### 用 CLAUDE.md 做持久化约束

每个 prompt 都写约束太累。把通用规则写进项目的 `CLAUDE.md`，Claude 每次启动都会自动读取。比如我博客项目的约束：

```yaml
# CLAUDE.md 片段
## 核心约束
- 不可逆操作必须确认（删除、覆写不可恢复的内容）
- 只做被要求的事，不自行扩展范围
- 不确定时问我，不猜

## 文章规范
- 每篇文章最多 2 个标签
- 代码块必须指定语言
- 修改后自动 commit + push
```

这样你每次说"写一篇文章"，Claude 自动遵守这些规则，不用在 prompt 里反复强调。

### 用文件引用代替文字描述

不要用文字描述代码长什么样，直接让 Claude 去读：

**低效写法**：> 我的数据库配置在 config 目录下那个 db 开头的文件里，里面有个连接池参数 max_open_conns，把它从 100 改成 200。

**高效写法**：

> 把 `config/db.go` 里的 `max_open_conns` 从 100 改成 200。

### 控制 Agent 的执行边界

对于有风险的操作，明确告诉 Claude 哪些不能碰：

```bash
> 给 user API 加分页功能。
> 约束：只改 internal/handler/user.go 和 internal/service/user.go，
> 不动数据库 schema，不改前端。
```

这种"白名单式"约束比"小心点"有效得多。

## 万能 Prompt 模板（可直接复制）

日常使用中，大部分 prompt 都可以套用这个结构：

```bash
# === Prompt 模板 ===
# 【目标】要做什么（一句话说清楚）
# 【上下文】相关文件路径、当前状态
# 【约束】什么不能变、什么必须满足
# 【参考】参照哪个文件/风格（可选）
# 【验收】怎么算做完（测试通过？手动验证？）

# === 实际使用示例 ===
# 【目标】给用户列表 API 加分页
# 【上下文】internal/handler/user.go 的 ListUsers 方法
# 【约束】不改数据库 schema，保持现有返回格式
# 【参考】参考 internal/handler/order.go 的 ListOrders 分页实现
# 【验收】单元测试通过 + 手动验证返回数据正确
```

不一定要每项都写，但 **目标永远是第一行**，**约束紧随其后**。养成这个习惯，你会发现 Claude Code 的输出质量明显提升。

---

写好 prompt 的本质就三件事：**说清目标、划清边界、给够上下文**。下次给 Claude Code 下指令之前，花 10 秒做三个检查：

1. 我的描述里有没有模糊词？（"优化""整理""改好"都算）
2. 我有没有说清楚什么不能动？
3. 有没有现成的代码可以当参考？

把这三个问题答完再发，你的效率会翻倍。
