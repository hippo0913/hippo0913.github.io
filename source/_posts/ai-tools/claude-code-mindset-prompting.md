# 怎么给 Claude Code 下指令：Prompt 技巧实战

上一篇翻车现场里，很多问题的根因都是"指令不够清晰"。这篇专门聊聊怎么给 Claude Code 下指令。

跟 Claude Code 对话和在网页版聊天完全不同——你不是在"问问题"，而是在"给一个 Agent 分配任务"。这个心智模型的转变，是写好 prompt 的关键。

## 四个核心原则

### 原则 1：说目标，不说步骤

Claude 是一个有判断力的执行者，不是一台只会按指令运转的机器。你告诉它"我要什么"，比告诉它"怎么做"效果更好。

**反例**：

> 先读一下 main.go，然后看一下 router 目录，找到 /api/users 这个路由，把它的 handler 改成从数据库查询而不是返回硬编码数据，然后运行测试，如果测试通过就提交。

**正例**：

> /api/users 路由目前返回硬编码数据，改成从数据库查询。确保现有测试通过后再提交。

正例更短，但信息更清晰。Claude 自己会去读文件、找路由、改代码、跑测试，这些步骤不需要你手把手教。

### 原则 2：加约束，不只是加描述

光说"改好一点"是不够的，要明确什么叫"好"。

**反例**：

> 把这个函数优化一下。

**正例**：

> 优化这个函数，要求：1）时间复杂度降到 O(n) 以下；2）不改变函数签名；3）保留现有测试。

三个约束（性能目标、接口不变、测试兼容）比一句"优化"有用得多。

### 原则 3：给参考，而不是从零开始

如果你心里有一个想要的效果，直接给 Claude 一个参考，比用文字描述快 10 倍。

**反例**：

> 写一个错误处理的中间件，要求能捕获 panic，返回 JSON 格式的错误响应，并且记录日志。

**正例**：

> 参考 `internal/middleware/auth.go` 的风格，写一个错误处理中间件。要求：捕获 panic、返回 JSON 错误响应、记录日志。

"参考某文件的风格"这六个字，省去了关于命名规范、包结构、错误码格式的一堆描述。

### 原则 4：复杂任务要拆分

一个大的 prompt 不如三个小的 prompt。不是因为 Claude 处理不了长文本，而是因为分步执行可以让你在每一步检查结果、调整方向。

**反例**：

> 帮我重构用户模块：先重新设计数据模型，然后改 API，然后更新前端调用，然后写测试。

**正例**（分三步）：

**第一步**：

> 看一下当前的用户数据模型，列出你觉得需要改进的地方，不要改代码，只给建议。

**第二步**（确认方案后）：

> 按照上一步讨论的方案，修改数据模型和数据库迁移脚本。只改模型层，不动 API。

**第三步**（模型改完后）：

> 基于 new model 更新 API 层和测试。确保所有测试通过。

## 六个常见场景的 Before / After

### 场景 1：修 Bug

**Before**：

> 这个 bug 修一下，用户登录后偶尔会 500。

**After**：

> 用户登录接口 `POST /api/login` 偶尔返回 500。可能和并发有关，因为重启后短时间内正常。请先看日志和代码定位原因，确认后再修。不要猜测。

关键点：**"先定位再修"** + **"不要猜测"**，防止 Claude 瞎改。

### 场景 2：加功能

**Before**：

> 加一个导出功能。

**After**：

> 给用户列表页加一个"导出 CSV"按钮。参考现有的"删除用户"按钮的代码风格。后端用 `GET /api/users/export`，返回 CSV 流。不需要分页，数据量通常在 1000 条以内。

关键点：**具体到 API 路径** + **给上下文（数据量）** + **参考已有代码**。

### 场景 3：重构

**Before**：

> 重构一下这个模块。

**After**：

> `internal/service/user.go` 已经 800 行了。把认证相关的方法提取到 `auth.go`，用户 CRUD 保留在 `user.go`。不改函数签名，不改外部行为，确保测试全过。

关键点：**明确重构范围** + **边界条件（不改签名、测试全过）**。

### 场景 4：写测试

**Before**：

> 给这个模块写测试。

**After**：

> 给 `internal/service/user.go` 的 `CreateUser` 和 `DeleteUser` 写单元测试。用项目已有的测试风格（参考 `internal/service/order_test.go`）。Mock 数据库层，不需要连真实数据库。

关键点：**指定函数** + **参考已有测试** + **明确 mock 策略**。

### 场景 5：查问题

**Before**：

> 为什么部署失败了？

**After**：

> GitHub Actions 构建失败了，错误信息是 `hexo generate` 返回非零退出码。配置文件在 `.github/workflows/pages.yml`。请检查最近的配置变更和 Markdown 文件是否有语法问题。

关键点：**带上错误信息** + **指出相关文件** + **限定排查方向**。

### 场景 6：批量操作

**Before**：

> 把所有文章的标签整理一下。

**After**：

> 检查 `source/_posts/` 下所有 Markdown 文件的 tags 字段，列出以下信息：
> 1. 只出现一次的标签（孤岛标签）
> 2. 可能重复的标签（意思相近但写法不同）
> 只列结果，不要自动修改，等我确认后再改。

关键点：**"只列结果不修改"**——批量操作最怕的就是自动执行后发现改错了。

## 一个万能模板

日常使用中，我大部分 prompt 都遵循这个结构：

```
[目标]：要做什么
[约束]：什么不能变、什么必须满足
[参考]：参照哪个文件/风格
[验收]：怎么算做完（测试通过？手动验证？）
```

不一定要四项都写，但目标永远是第一行。试试看，你会发现 Claude Code 的输出质量明显提升。
