# 上下文爆了怎么办：Claude Code 长任务生存指南

有次我用 Claude Code 批量重写 20 篇文档，顺序处理到第 5 篇时，它开始把文件 A 的内容写到文件 B，CLAUDE.md 里明确禁止的操作它也照做不误。不是 Claude 变笨了——上下文窗口满了，早期的指令和约定被新内容挤了出去。

上下文窗口（Context Window）就像一张固定大小的桌子，每条对话、每个文件内容都要占位置。桌上的东西越多，新放上去的东西就越容易把旧的挤下去。当 Claude 丢失了关键的项目约定，输出质量就会断崖式下降。

这篇文章解决一个问题：**怎么在长任务中保持 Claude Code 的输出质量**。结构是：识别溢出信号 → 三级应对策略 → 预防性设计 → 实战复盘。

## 三个预警信号与诊断方法

上下文溢出不是突然发生的，它会先给出三个明确信号。识别越早，恢复成本越低。

### 信号 1：Claude 开始重复操作

刚搜索过的文件又搜索一遍，刚修完的 bug 又修了一遍。这说明它对"刚才做了什么"的记忆已经开始模糊，只能靠重新搜索来确认状态。

### 信号 2：忽略 CLAUDE.md 的规则

CLAUDE.md 里写了"错误返回用统一格式"，但它突然开始用另一种格式。这不是故意违抗——CLAUDE.md 的内容被挤到了上下文边缘，优先级降低了。

### 信号 3：文件内容搞混

修改文件 A 的内容写到了文件 B。这是上下文饱和的典型症状，说明它已经无法准确区分不同文件的上下文了。

**怎么查看上下文用量**：在 Claude Code 里输入 `/context`，可以看到当前上下文的占用比例。超过 70% 就要警惕了。

| 信号 | 具体表现 | 严重程度 | 推荐应对 |
|------|---------|---------|---------|
| 重复操作 | 同一搜索/修改执行两遍 | 中 | `/clear` + 精简描述即可恢复 |
| 忽略规则 | 违反 CLAUDE.md 中的明确约定 | 高 | 必须重启，补充关键规则到 prompt |
| 文件搞混 | A 文件的内容写到 B 文件 | 紧急 | 立即停止，用进度文件重启 |

## 应对策略：从轻量到重度的三级方案

### 方案 1：轻量重启——`/clear` + 精简描述

适用场景：简单的上下文溢出，任务本身步骤不多。

```bash
# 第 1 步：清空上下文
/clear

# 第 2 步：在新会话里用一两句话描述当前状态和下一步目标
# 不要重复之前的所有对话，只说"到哪了"+"接下来做什么"
```

恢复提示词模板：

```
当前状态：Device CRUD API 已完成，测试全部通过。
项目约定：参考 CLAUDE.md。
下一步：给 SensorData 模型实现类似的 CRUD，参考 Device 的代码结构。
```

**关键点**：Claude 会从代码文件里自动读取它需要的细节，你只需要告诉它起点和方向。

### 方案 2：进度文件重启

适用场景：多步骤任务，步骤之间有依赖关系。

先设计一个 JSON 格式的进度文件：

```json
{
  "task": "重写官方文档系列",
  "total": 20,
  "completed": ["overview.md", "quickstart.md", "setup.md"],
  "in_progress": "best-practices.md",
  "failed": {
    "hooks.md": "文件截断，需要重新处理"
  }
}
```

每次 `/clear` 后，在新会话里让 Claude 读取进度文件恢复断点：

```
读取 .claude/scoring/progress/official-doc.json，继续处理下一个未完成的文件。
每完成一个文件就更新进度文件。
```

**关键点**：进度文件是机器可读的，Claude 能精确恢复到断点，不遗漏、不重复。

### 方案 3：完整拆分重启

适用场景：任务本身就很复杂，一个会话根本装不下。

拆分原则——按层拆分，每层一个独立会话：

```
会话 1：分析模块结构，输出重构方案到 REFACTOR-PLAN.md
会话 2：读取 REFACTOR-PLAN.md，重构数据层
会话 3：读取 REFACTOR-PLAN.md，重构业务层
会话 4：读取 REFACTOR-PLAN.md，更新测试
```

每个子会话的 prompt 模板：

```
这是 {项目名} 的重构任务，第 {N}/{Total} 步。
计划文件：{PLAN_FILE}
上一步完成状态：{简要描述}
本步目标：{具体目标}
完成后更新计划文件中对应的步骤状态。
```

## 预防性设计：不让上下文爆掉

应对策略是救火，预防性设计才是根本。

### 任务拆分的实操方法

三种拆分粒度，按需选择：

- **按层级拆**：数据层 → 业务层 → 接口层 → 测试，适合模块重构
- **按文件拆**：每个会话只动 2-3 个文件，适合大范围格式修改
- **按功能拆**：每个会话只做一个功能点，适合需求开发

### `max-turns` 参数详解

启动任务时设置轮次上限，强制控制上下文消耗：

```bash
# 单文件小修改：3-5 轮够用
claude --max-turns 5 "修复 login.js 中的空指针异常"

# 中等任务：10 轮
claude --max-turns 10 "给 Device 模型加软删除功能"

# 复杂任务：15 轮，超出说明任务需要拆分
claude --max-turns 15 "重构 user 模块的数据层"
```

如果任务在设定轮次内没做完，说明任务本身需要拆分，而不是需要更多轮次。

### Subagent 隔离批量任务

批量任务（改 20 个文件、处理 10 个模块）最容易撑爆上下文。用 Subagent 把每个子任务隔离在独立的上下文窗口里：

> 用 Subagent 并行处理 source/_posts/ 下每个 Markdown 文件的格式修正。每个 Subagent 只处理一个文件。

每个 Subagent 有自己独立的上下文窗口，互不干扰。

**注意事项**：
- Subagent 之间不能直接共享状态，需要通过文件传递信息
- 每个子任务要足够独立，不能有复杂的跨文件依赖
- 适合格式修正、批量重命名等机械性操作

| 预防手段 | 适用场景 | 核心参数/方法 |
|---------|---------|-------------|
| 按层级拆分 | 模块重构 | 每会话一层，通过计划文件衔接 |
| 按文件拆分 | 格式修改、批量替换 | 每会话 2-3 个文件 |
| 按功能拆分 | 需求开发 | 每会话一个功能点 |
| `max-turns` | 所有中大型任务 | 5/10/15，按复杂度选 |
| Subagent | 批量机械操作 | 每个子任务独立，通过文件协调 |

## 实战复盘：批量重写 20 篇文档

这个案例来自我的真实项目——用 Claude Code 批量重写博客的 20 篇官方文档翻译稿。

### 问题：顺序处理到第 5 篇上下文饱和

一开始用一个会话顺序处理：读取原文 → 按评分标准重写 → 自检 → 下一个。到第 5 篇时，Claude 开始忘记评分标准，忽略 CLAUDE.md 里的格式要求，上下文占用超过 90%。

### 方案演进：三次迭代

**第 1 版：单会话 + 手动重启**

每 5 篇 `/clear` 一次，手动告诉 Claude 从哪篇继续。问题是每次重启都要重新描述评分标准，容易遗漏。

**第 2 版：进度文件断点恢复**

设计了一个 JSON 进度文件（就是前面方案 2 的结构），每次重启后让 Claude 读文件恢复断点。进步很大，但到第 15 篇左右，单次会话处理 5 篇仍然会饱和。

**第 3 版：编排器 + Subagent 并行（最终方案）**

最终的架构是这样的：

```bash
# 编排器（Orchestrator）：主会话只做调度，不处理具体文章
# 读取进度文件 → 启动 Subagent → 检查结果 → 更新进度

# 每篇文章一个独立 Subagent
claude --max-turns 20 "按 .claude/scoring/profiles/official-doc.yaml 标准
重写 source/_posts/ai-tools/official-docs/hooks.md。
完成后更新 .claude/scoring/progress/official-doc.json 中的状态。"
```

核心思路：主会话只做调度，不碰文件内容。每个 Subagent 独立处理一篇文章，有自己的完整上下文，不会互相干扰。这样 20 篇文章并行处理，单次成功率从 60% 提升到 95% 以上。

## 总结与上下文管理速查表

| 任务复杂度 | 典型场景 | 推荐策略 | 关键动作 |
|-----------|---------|---------|---------|
| 简单（1-3 轮） | 单文件 bug 修复 | 无需特殊处理 | 正常执行 |
| 中等（5-10 轮） | 单功能开发、配置修改 | `max-turns` 限制 | `claude --max-turns 10` |
| 复杂（10-20 轮） | 模块重构、多文件修改 | 拆分 + 进度文件 | 按层/按功能拆，进度文件衔接 |
| 批量（20+ 子任务） | 批量重写、全项目扫描 | 编排器 + Subagent | 每个子任务独立上下文 |

记住三个关键动作：

1. **留意预警信号**：重复操作、忽略规则、文件搞混，出现任何一个就该行动
2. **主动重启**：`/context` 显示 70% 时就该用 `/clear` 或进度文件重启，别等到 90%
3. **预防性设计**：大任务拆小会话，批量任务用 Subagent，从一开始就控制上下文消耗
