# 上下文爆了怎么办：Claude Code 长任务生存指南

在前面的 Go 后端实战里，你可能注意到一个隐含的问题：当会话持续很久、来回很多轮时，Claude 的输出质量会下降。

这不是 Claude 变笨了，而是上下文窗口满了。就像你的工作台上摆满了东西，再多放一张纸就会掉下去。

这篇聊聊怎么在长任务中管理上下文。

<!-- more -->

---

## 三个预警信号

上下文溢出不是突然发生的，它会先出现这些症状：

### 信号 1：Claude 开始重复自己

同样的搜索操作做了两遍，或者刚修完的 bug 又修了一遍。这说明它对"刚才做了什么"的记忆已经开始模糊。

### 信号 2：忽略了 CLAUDE.md 的规则

你明明在 CLAUDE.md 里写了"错误返回用统一格式"，但它突然开始用另一种格式。这不是它故意违抗，而是 CLAUDE.md 的内容被挤到了上下文边缘，优先级降低了。

### 信号 3：文件搞混

修改文件 A 的内容写到了文件 B。这在翻车现场那篇讲过，是上下文饱和的典型症状。

**怎么查看当前上下文用量**：在 Claude Code 里输入 `/context` 可以看到大致的上下文占比。超过 70% 就要警惕了。

---

## 策略 1：轻量重启——`/clear` + 精简描述

适用于：简单的上下文溢出，任务本身不复杂。

```bash
# 清空上下文
/clear

# 在新会话里用一两句话描述当前状态和下一步目标
当前状态：Device CRUD API 已完成，测试通过。
下一步：给 SensorData 模型实现类似的 CRUD。
```

**要点**：不要在新会话里重复之前所有的对话，只说"当前到哪了"+"接下来要做什么"。Claude 会从代码文件里读取它需要的细节。

---

## 策略 2：文档化重启——进度文件

适用于：复杂任务，有多步骤依赖关系。

当任务特别复杂时（比如上一章提到的并行重写 20 篇博客），我会用一个进度文件来记录状态：

```json
{
  "task": "重写官方文档系列",
  "total": 20,
  "completed": ["overview.md", "quickstart.md", "setup.md"],
  "in_progress": "best-practices.md",
  "failed": {
    "hooks.md": "文件截断，需要重新处理"
  }
}
```

每次 `/clear` 后，在新会话里让 Claude 读这个文件就能恢复进度：

> 读取 `.claude/scoring/progress/official-doc.json`，继续处理下一个未完成的文件。

**要点**：进度文件是机器可读的，Claude 可以精确恢复到断点，不会遗漏。

---

## 策略 3：预防性设计——拆任务、定边界

最理想的状况是不让上下文溢出。三个习惯可以帮到你：

### 习惯 1：大任务拆成小会话

不要在一个会话里说"重构整个模块"。拆成：

- 会话 1：分析模块结构，列重构方案
- 会话 2：重构数据层
- 会话 3：重构业务层
- 会话 4：更新测试

每个会话的目标单一，上下文不太可能溢出。

### 习惯 2：用 `max-turns` 限制

在启动复杂任务时设置轮次上限：

```bash
claude --max-turns 10 "给 Device 模型加软删除功能"
```

10 轮通常够完成一个中等任务。如果没做完，说明任务可能需要拆分。

### 习惯 3：用 Subagent 处理批量任务

批量任务（改 20 个文件、处理 10 个模块）最容易撑爆上下文。用 Subagent 把每个子任务隔离在独立的上下文里：

> 用 Subagent 并行处理 source/_posts/ 下每个 Markdown 文件的格式修正。每个 Subagent 只处理一个文件。

每个 Subagent 有自己独立的上下文窗口，不会互相干扰。

---

## 上下文预算速查

不同类型的任务，大致需要的上下文量：

| 任务类型 | 建议轮次 | 是否需要拆分 |
|----------|---------|-------------|
| 单文件修改 | 3-5 轮 | 不需要 |
| 多文件功能开发 | 10-15 轮 | 可能需要 |
| 模块级重构 | 15-20 轮 | 建议按层拆分 |
| 全项目批量操作 | 不设限 | 必须用 Subagent |

这不是硬规则，而是一个参考。实际使用中，留意前面说的三个预警信号，比死记数字更重要。

## 真实案例：20 篇文档重写

我之前用 Claude Code 并行重写 20 篇博客文章，一开始在一个会话里顺序处理，到第 5 篇时上下文就接近饱和了。

后来改成 Subagent 方案：

1. 编排器读取进度文件，确定哪些文章需要处理
2. 为每篇文章启动独立的 Subagent
3. 每个 Subagent 只处理一篇文章，完成后更新进度文件
4. 编排器检查结果，决定是否需要迭代

这样每个 Subagent 的上下文都很干净，不会出现"处理到第 10 篇时忘了第 1 篇的要求"的问题。

---

## 总结

上下文管理不是高级技巧，而是**日常使用的必备习惯**。三个关键动作：

1. **留意预警信号**：重复、忽略规则、文件搞混
2. **主动重启**：不要等到完全溢出，70% 时就该行动
3. **预防性设计**：大任务拆小会话，批量任务用 Subagent

做到了这三点，你会发现长任务的成功率明显提高。
