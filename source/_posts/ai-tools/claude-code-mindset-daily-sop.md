# Claude Code 日常 SOP：我的标准操作流程

上周我在博客项目里写新文章，Claude Code 自作主张把另外三篇文章的标签也改了——它觉得"标签不够规范"。等我 `git diff` 一看，改动散布在四个文件里，真正要我改的那个倒只改了一行。

这不是 Claude 不聪明，是我没给它足够的约束。从那以后我开始固化一套标准操作流程（SOP），把前面几篇讲的 prompt 技巧、信任判断、踩坑经验串成一条线。按流程走，翻车率降了大半。

## 开始新任务：3 件事

每次打开 Claude Code 开始新任务，我做三件事。耗时不到一分钟，但省下的调试时间按小时计。

### 1. 确认目录

多项目并行时最容易翻车——你以为在改后端 API，其实在改博客主题。

```bash
# 养成习惯，第一条命令永远是这个
pwd
# /home/yy/workspace/projects/l4_cloud/backend
```

如果目录不对，直接 `cd` 到正确项目，或者开一个新的终端窗口。千万别在错误目录下开始工作，Claude 会忠实地改错项目。

### 2. 一句话说清目标

好的 prompt 和差的 prompt，效果天差地别：

```bash
# 反面案例：模糊、多目标
claude "优化一下用户体验"

# 正面案例：明确、单一、有边界
claude "给用户列表页加搜索框，支持按姓名和邮箱模糊搜索，参考现有的分页组件实现"
```

关键原则：**做什么** + **做到什么程度** + **参考什么**。三个要素齐了，Claude 就不会自由发挥。

### 3. 让 Claude 先读代码再动手

跳过这步是我踩过最多次的坑。Claude 没看过现有实现就直接动手，结果要么重复造轮子，要么改了不该改的地方。

```bash
# 如果是修改现有代码，第一条指令永远是这样
claude "先看一下当前的用户列表实现（src/pages/UserList.tsx），告诉我你打算怎么改，不要直接改代码。"
```

它返回的修改计划就是你的审查依据。觉得计划不对，调整后再让它动手；计划合理，一句"按这个计划执行"就行。30 秒的投资，换来避免半小时的返工。

## 任务执行中：检查点模式

我不用 Claude 一次性跑完所有步骤。而是用"检查点"循环：Claude 做 3-5 步，我审查一次，确认后下一轮。

| 循环阶段 | 你做什么 | 验收标准 |
|---|---|---|
| Claude 执行 | 观察输出，看它是否偏离目标 | 无未授权的文件改动 |
| 审查 diff | `git --no-pager diff` 看改动 | 文件范围正确，无多余删除 |
| 确认或调整 | 合格说"继续"，不合格给纠正 | 每轮改动可独立回退 |

### 什么时候打断

不是每个检查点都要等 Claude 主动停。出现以下信号，立刻打断：

- **改了 5 个以上文件**——一个功能点不该波及这么多文件，大概率跑偏了
- **开始改你没提到的文件**——Claude 在"顺手优化"，必须确认是否必要
- **连续 3 次搜索-编辑循环**——它在原地打转，需要你给新方向
- **输出中频繁出现"让我重新思考"**——上下文已经混乱，考虑 `/clear`

打断方式很简单：直接说话就行，不用等它完成当前操作。

### 怎么审查

```bash
git --no-pager diff           # 看整体改动范围
git --no-pager diff --stat    # 快速看改了几个文件、每个文件改了几行
```

审查清单：

| 检查项 | 关注点 | 危险信号 |
|---|---|---|
| 文件范围 | 只改了目标相关的文件 | 出现无关文件 |
| 删除内容 | 删掉的代码是否还在用 | 大段删除且无替换 |
| 新增风格 | 命名、缩进与现有代码一致 | 引入新的代码风格 |
| 硬编码 | 配置值是否提取为常量 | 出现魔法数字 |
| 注释 | 关键逻辑有注释说明 | 无意义的注释噪声 |

如果检查通过，说"继续"或"提交"。有问题就具体指出哪里不对，让 Claude 修正。

## 事情不对劲时：升级路径

不是每次都能顺利推进。遇到问题时，我按四级路径逐步升级：

| 级别 | 场景 | 操作 | 示例 |
|---|---|---|---|
| Level 1 | 方向偏了一点 | 在当前会话调整 prompt | "方向不对，我要的是 X 不是 Y，回退重做" |
| Level 2 | 完全跑偏 / 上下文混乱 | `/clear` 重开会话 | 用更精确的 prompt 从头开始 |
| Level 3 | 反复犯同一个错 | 写入 CLAUDE.md | 把正确规则固化到项目配置 |
| Level 4 | 写了规则还不遵守 | 加 Hook 强制执行 | 自动化检查，不可能被跳过 |

### Level 1：调整 prompt

大部分问题在这个级别就能解决。Claude 理解错了需求，纠正一下就好：

```
你改的方向不太对。我需要的是在前端加过滤，不是在后端改查询。
回退刚才的改动，只改 UserList.tsx 这一个文件。
```

### Level 2：清空重来

上下文太长时，Claude 会"记住"之前的错误方向，反复往回扯。这时候别硬撑：

```bash
/clear
# 用更精确的 prompt 重新开始
claude "只修改 UserList.tsx，在前端加一个搜索框过滤用户列表。不要改后端代码。"
```

### Level 3：写入规则

Claude 反复犯同一个错误——比如我的项目要求错误码用五位数字，它总是用三位。这不是 Claude 的问题，是你的规则没写清楚。

```markdown
# 在 CLAUDE.md 中新增
## 错误码规范
- 业务错误码格式：五位数字，前两位是模块编号
- 示例：`40001`（用户模块）、`50012`（订单模块）
- 不要用 HTTP 状态码作为业务错误码
```

CLAUDE.md 是软约束——Claude 会尽量遵守，但不保证每次都记得。

### Level 4：加 Hook

写了规则还是偶尔违反？把它升级成 Hook，变成硬约束：

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "git commit",
      "command": "cd /path/to/project && go test ./..."
    }]
  }
}
```

这个 Hook 的意思是：每次 Claude 要执行 `git commit` 之前，自动跑一遍测试。测试不过，提交就被拦截。Hook 是系统级拦截，不可能被跳过——这就是它和 CLAUDE.md 规则的本质区别。

## 完成任务：3 步收尾

### 1. 审查最终 diff

```bash
git --no-pager diff           # 完整看所有改动
git --no-pager diff --stat    # 改动统计
```

这是最后一道防线。重点看三个问题：
- 改动是否都是你要求的？
- 有没有遗漏的文件没改到？
- 有没有调试代码或临时代码残留？

### 2. 本地验证

不同类型的任务，验证方式不同：

| 任务类型 | 验证命令 | 确认要点 |
|---|---|---|
| 写后端代码 | `go test ./...` 或 `npm test` | 测试全部通过 |
| 改项目配置 | `hexo clean && hexo server` | 本地启动正常 |
| 写博客文章 | `hexo server` → 浏览器预览 | 排版、链接、图片正常 |
| 改 CI/CD | 检查 workflow 文件语法 | 触发条件、步骤正确 |
| 修 bug | 复现原 bug 的步骤 | 确认已修复且无新问题 |

### 3. 提交推送

```bash
git add src/pages/UserList.tsx          # 只 add 相关文件
git commit -m "feat: 用户列表页加搜索功能"
git push
```

提交信息格式遵循约定式提交（Conventional Commits）：
- `feat:` 新功能
- `fix:` 修 bug
- `post:` 博客文章
- `docs:` 文档变更
- `refactor:` 重构

**永远不要 `git add .`**——这会把所有改动一股脑塞进去，包括你不想要的临时文件。

## 每周维护：10 分钟

每周花 10 分钟做一轮维护，保持项目配置的健康度。

### 审查 CLAUDE.md

```bash
wc -l CLAUDE.md   # 看总行数
```

检查清单：
- 上周新增的规则还有必要吗？完成的项目规则可以删掉
- 有没有项目变更导致规则过时？比如换了测试框架
- 总行数超过 200 行了吗？超过就该精简，规则太多 Claude 反而记不住

### 检查 Hooks 触发记录

看看 `.claude-output/logs/` 下的日志，确认 Hooks 正常工作：
- 误拦截（不该拦的拦了）→ 调整 matcher
- 漏拦截（该拦的没拦）→ 补充 matcher

### 清理残留

```bash
# 检查是否有遗留的临时文件
git status
# 删掉不需要的文件，更新进度记录
```

## 总结

整篇 SOP 浓缩成一张表：

| 阶段 | 动作 | 关键命令/操作 |
|---|---|---|
| 开始 | 确认目录 | `pwd` |
| 开始 | 说清目标 | 明确 prompt：做什么+程度+参考 |
| 开始 | 先读后改 | "先看代码，告诉我计划，不要直接改" |
| 执行 | 检查点循环 | 每 3-5 步 `git diff` 审查一次 |
| 遇到问题 | L1-L4 升级 | 调整 → `/clear` → CLAUDE.md → Hook |
| 收尾 | 审查+验证+提交 | `git diff` → 本地验证 → `git add/commit/push` |
| 每周 | 维护配置 | 审查 CLAUDE.md + Hooks + 清理残留 |

SOP 不需要复杂，需要的是每次都照着走。这套流程让我把大部分翻车扼杀在发生之前，而不是事后花时间擦屁股。
