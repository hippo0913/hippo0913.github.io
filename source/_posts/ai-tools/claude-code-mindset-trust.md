# 什么时候该信任 Claude Code，什么时候自己来

用 Claude Code 越久，越会遇到一个问题：它 3 分钟写完的代码，我要不要直接提交？

全盘信任肯定不行——我已经在翻车现场那篇讲过教训了。但逐行审查又太慢，失去了用 AI 提效的意义。

我用了一段时间后，总结出一个简单的"红黄绿灯"判断框架，分享给你。

<!-- more -->

---

## 绿灯：放心让它干

这些场景我基本不审查细节，只看最终结果：

**样板代码**。CRUD 的增删改查、数据模型定义、路由注册——这些有固定模式的代码，Claude 写得比大多数人快且正确。

**文档和注释**。README、API 文档、代码注释。就算写得不够好，改起来也很快，不会引入 bug。

**格式化和重构**。重命名变量、调整 import 顺序、按 lint 规则修改。这类任务目标明确、结果可预测。

**写测试用例**。给一个函数，让 Claude 生成各种边界情况的测试。它考虑的边界条件通常比我全面。

**从模板生成代码**。新建一个配置文件、写一个 Dockerfile、生成 CI 配置——模板化的东西它很擅长。

**判断标准**：如果出错了，我能 5 分钟内发现并修好 → 绿灯。

---

## 黄灯：让它干，但要审查

这些场景我会让它做，但完成后会仔细看 diff：

**业务逻辑**。比如"用户积分超过 1000 时自动升级会员等级"这种逻辑。Claude 能写，但它不了解你的业务全貌，可能遗漏边界情况。

**数据库 Schema 变更**。建表、加字段、改索引。写错了影响很大，但 Claude 写的初版通常是个不错的起点。

**API 设计**。接口路径、请求/响应格式、错误码。Claude 倾向于用 RESTful 标准风格，但不一定符合你团队已有的约定。

**配置变更**。修改 YAML 配置、环境变量、权限设置。一行配置错误可能导致整个服务挂掉。

**判断标准**：如果出错了，要花 30 分钟以上排查 → 黄灯。

---

## 红灯：自己来，或者极端审查

这些场景我不用 Claude，或者用它写完之后逐行审查：

**安全相关代码**。认证、授权、加密、密钥管理。这类代码一个疏忽就是漏洞，不值得冒险。

**数据迁移**。生产环境的数据库迁移脚本。跑错了数据就没了，必须自己写或者在测试环境反复验证。

**涉及金钱的逻辑**。支付、计费、折扣计算。小数点错一位就是真金白银的损失。

**核心架构决策**。选框架、定分层结构、设计模块边界。这些决策影响长远，需要你自己权衡。

**判断标准**：如果出错了，不可逆或损失巨大 → 红灯。

---

## 一个简单的判断公式

不想记上面那些分类的话，用一个公式：

> **信任程度 = 恢复速度 × 熟悉程度**

- **恢复速度快**（git rollback 能救、只是文档不影响运行）→ 偏向信任
- **恢复速度慢**（数据库改了、线上服务挂了）→ 偏向不信任
- **你对这块熟悉**（一眼能看出问题）→ 偏向信任
- **你不熟悉**（不确定对不对）→ 偏向不信任

两个维度都高 → 绿灯。任一维度低 → 至少黄灯。

---

## 审查清单

当你决定审查 Claude 的输出时，重点看这些：

1. **文件路径**——它有没有改错文件？（翻车现场第 2 式）
2. **删除的内容**——它删掉的代码里有没有你还在用的逻辑？
3. **硬编码值**——密钥、URL、magic number 是否正确？
4. **错误处理**——它有没有吞掉错误或者加了不必要的 fallback？
5. **边界情况**——空值、并发、超大输入，它处理了吗？
6. **风格一致**——命名、格式、目录结构是否符合项目惯例？

不需要逐行看。先用 `git diff` 看整体改动范围，如果范围合理，再聚焦看上面 6 点。

## 我的实际做法

日常开发中，我大概这样分配：

- 60% 的任务是绿灯——让 Claude 做，我只看结果
- 30% 的任务是黄灯——让 Claude 做初版，我来审查和调整
- 10% 的任务是红灯——自己做，或者用 Claude 做 research 但自己写代码

这个比例不是固定的。新项目早期黄灯比例高（因为项目规范还没建立），等项目成熟了绿灯比例会上升。关键是**根据自己的恢复能力和熟悉程度动态调整**，而不是一刀切。
