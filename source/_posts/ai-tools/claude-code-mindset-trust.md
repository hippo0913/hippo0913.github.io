# 什么时候该信任 Claude Code，什么时候自己来

用 Claude Code 越久，越会遇到一个核心问题：它 3 分钟写完的代码，我能不能直接提交？全盘信任不现实，逐行审查又太慢，等于白用 AI 提效。

这篇文章给你一个可落地的判断框架，让你在每次交给 Claude 任务之前，快速决定放手到什么程度、审查看哪些地方。

## 红黄绿灯信任框架

我把日常开发任务分成三类，用红黄绿灯标记信任等级：

| 颜色 | 场景类型 | 判断标准 | 审查力度 | 示例 |
|---|---|---|---|---|
| 绿灯 | 样板代码、文档、格式化 | 出错 5 分钟内能发现并修好 | 看结果即可 | CRUD 模型、README、lint 修复 |
| 黄灯 | 业务逻辑、配置变更、API 设计 | 出错需 30 分钟以上排查 | 必须看 diff | 积分规则、数据库 Schema、环境变量 |
| 红灯 | 安全代码、数据迁移、涉及金钱 | 出错不可逆或损失巨大 | 逐行审查或自己写 | 认证逻辑、生产迁移脚本、支付计算 |

### 绿灯：放心让它干

绿灯任务的特征是有固定模式、结果可预测。比如让 Claude 生成一个 CRUD 数据模型：

```bash
# 典型绿灯任务的 prompt
> 给我写一个 Go 的 User 模型，包含 ID、Name、Email、CreatedAt 字段，
> 同时生成对应的 CRUD handler，用 Gin 框架。
```

Claude 输出的模型定义和路由注册基本不会出错——这类代码模板化程度高，就算有小问题，编译或测试一跑就能发现。验收方式也很简单：

```bash
# 绿灯任务快速验收：编译通过 + 测试通过就够了
go build ./... && go test ./... 
```

绿灯任务我基本不审查细节，只看最终结果是否通过验证。

### 黄灯：让它干，但要审查 diff

黄灯任务需要 Claude 出初版，但完成后必须用 `git diff` 仔细看改动。比如修改数据库 Schema，我会重点关注：

```bash
# 查看完整 diff，确认改动范围
git diff --stat                # 先看改了哪些文件
git diff                       # 再看具体改动

# 重点关注：字段类型、默认值、索引、是否误删了其他字段
```

审查黄灯任务的核心关注点：改动范围是否超出预期？有没有遗漏的边界情况？配置值是否正确？

### 红灯：自己来，或极端审查

红灯任务的典型代表是安全相关代码。比如 JWT 认证逻辑——Claude 可能写出功能正确但存在安全漏洞的代码：

```go
// Claude 可能生成这样的代码——功能正确但有隐患
token, err := jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
    return []byte("my-secret-key"), nil  // 硬编码密钥，且未校验签名算法
})
```

这段代码能跑通，但没有校验 `SigningMethod`（攻击者可以用 `none` 算法绕过），密钥也硬编码了。安全代码的审查标准不是"能跑就行"，而是"每个细节都要经得起攻击"。

## 判断公式与决策流程

不想逐个对照表格的话，用一个公式快速判断：

> **信任程度 = 恢复速度 x 熟悉程度**

- 恢复速度快（`git revert` 能救、只是文档不影响运行）→ 偏向信任
- 恢复速度慢（数据库改了、线上服务挂了）→ 偏向不信任
- 你对这块熟悉（一眼能看出问题）→ 偏向信任
- 你不熟悉（不确定对不对）→ 偏向不信任

两个维度都高 → 绿灯。任一维度低 → 至少黄灯。

### 走一遍完整决策流程

假设任务：给博客加一个文章自动生成摘要的功能。

1. **恢复速度**：改的是生成逻辑，`git revert` 一条命令就能回滚 → 快
2. **熟悉程度**：我对 Hexo 模板引擎很熟，改错了能立刻看出来 → 熟悉
3. **结论**：绿灯，让 Claude 写，我跑一下 `hexo server` 看效果就行

```bash
# 绿灯任务验收：本地预览确认效果
hexo clean && hexo server
# 浏览器打开 http://localhost:4000 确认摘要生成正确
```

换个任务：修改生产环境的数据库迁移脚本。恢复速度慢（跑错了数据可能没了），我对这块的熟悉程度是中等 → **黄灯偏红**，必须让 Claude 出初版，在测试环境反复验证后再上生产。

## 审查实战：拿到 Claude 的输出后怎么做

决定审查后，按这个清单逐项检查：

| 序号 | 检查项 | 具体做法 |
|---|---|---|
| 1 | 文件路径 | `git diff --name-only` 确认只改了目标文件 |
| 2 | 删除的内容 | `git diff` 里找 `-` 开头的行，确认没误删有用逻辑 |
| 3 | 硬编码值 | 搜索密钥、URL、magic number，确认值是否正确 |
| 4 | 错误处理 | 检查是否有吞错（空 `catch`）或不必要的 fallback |
| 5 | 边界情况 | 空值、并发、超大输入，是否都有处理 |
| 6 | 风格一致 | 命名、格式、目录结构是否符合项目惯例 |

不需要逐行看。先 `git diff --stat` 看改动范围，范围合理再聚焦上面 6 点。对于反复出现的检查项（比如风格一致、硬编码值），可以在项目的 `CLAUDE.md` 里声明规则，让 Claude 在生成代码时就遵守，减少审查工作量。

## 我的实际比例与动态调整

日常开发中，我大概这样分配：

- **60% 绿灯**——让 Claude 做，我只看结果
- **30% 黄灯**——让 Claude 做初版，我来审查和调整
- **10% 红灯**——自己做，或用 Claude 做 research 但自己写代码

这个比例不是固定的。新项目早期黄灯比例高（项目规范还没建立），等规范成熟后绿灯比例会上升。我会在项目的 `CLAUDE.md` 里声明信任策略，让 Claude 自己也知道哪些事可以放手做：

```yaml
# 在项目 CLAUDE.md 中声明信任策略示例

## 信任等级

### 绿灯（直接执行，无需确认）
- 格式化代码、修复 lint 错误
- 更新文档和注释
- 从现有模式生成样板代码

### 黄灯（执行后需要我看 diff）
- 修改业务逻辑
- 变更配置文件
- 添加新的依赖

### 红灯（必须我先确认再执行）
- 修改认证/授权相关代码
- 数据库 migration
- 涉及支付或计费的逻辑
```

关键是**根据自己的恢复能力和熟悉程度动态调整**，而不是一刀切。信任框架的目标不是限制 Claude，而是让你的审查精力花在刀刃上。

## 总结

1. 用红黄绿灯框架给每个任务分级，绿灯放手、黄灯审查 diff、红灯自己来。
2. 公式"恢复速度 x 熟悉程度"帮你快速判断，不用每次对照表格。
3. 把信任策略写进 `CLAUDE.md`，让 Claude 也知道边界在哪，减少来回确认。

下一步：打开你最常用的项目，花 5 分钟把常见任务分个红黄绿灯，写进 `CLAUDE.md`。之后的每次协作，你会发现自己越来越清楚什么时候该放手。
