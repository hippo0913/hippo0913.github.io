# 写好 CLAUDE.md 的 7 个反模式

CLAUDE.md 是 Claude Code 使用中最重要的文件——它决定了 Claude 理解你项目的方式。写得好，Claude 像一个熟悉你项目的老同事；写得不好，它像一个刚入职还搞不清状况的新人。

但"写得不好"有很多种形式。这篇文章列出 7 个我犯过的反模式，每个都附上正确做法。

<!-- more -->

---

## 反模式 1：大而全——700 行的 CLAUDE.md

**表现**：把项目里的所有规范、约定、历史决策都塞进一个 CLAUDE.md。

**问题**：CLAUDE.md 的内容会占用上下文窗口。700 行的 CLAUDE.md 可能占了 15-20% 的上下文空间，留给实际工作的空间就少了。而且信息量太大，Claude 反而抓不住重点。

**正确做法**：控制在 100-200 行以内。只写 Claude 在日常工作中真正需要的规则。项目的历史背景、架构决策记录可以放在其他文档里，Claude 需要时可以主动去读。

```markdown
# 好的 CLAUDE.md 结构（示例）

## 项目信息（5-10 行）
框架、语言、数据库、目录结构

## 代码规范（10-20 行）
命名、错误处理、日志等关键约定

## 注意事项（5-10 行）
不能做的事情、安全要求

## 常用命令（5 行）
build、test、deploy
```

## 反模式 2：只有"不要"，没有"要"

**表现**：

```markdown
- 不要用 fmt.Println
- 不要硬编码
- 不要忽略错误
```

**问题**：Claude 知道不能做什么，但不知道应该怎么做。结果它可能会用另一种你不喜欢的方式来替代，因为你没告诉它正确的方式是什么。

**正确做法**：每条"不要"配上"要"：

```markdown
- 日志用 internal/logger，不要用 fmt.Println
- 密钥从环境变量读取，不要硬编码
- 所有错误必须显式处理并返回，不要用 _ 忽略
```

---

## 反模式 3：全局 CLAUDE.md 写了项目特有的规则

**表现**：在 `~/.claude/CLAUDE.md`（全局配置）里写了"数据库用 PostgreSQL"、"API 用 Gin 框架"。

**问题**：全局 CLAUDE.md 对所有项目生效。你在博客项目里也写 Go 框架规则，Claude 就会在 Hexo 博客项目里尝试套用 Go 的约定。

**正确做法**：

- 全局 CLAUDE.md：只放**通用的工作习惯**（语言偏好、错误处理原则、终端习惯等）
- 项目 CLAUDE.md：放**项目特有的约定**（框架、目录结构、命名规范等）

---

## 反模式 4：用 Claude 生成 CLAUDE.md

**表现**：开一个空项目，让 Claude "帮我写一份 CLAUDE.md"。

**问题**：Claude 生成的 CLAUDE.md 通常是泛泛的标准规范（"遵循 Go 最佳实践"、"写好注释"），缺少你自己才知道的项目细节。我在 Go 后端项目里踩过这个坑——Claude 生成的 CLAUDE.md 写了"使用标准 HTTP 错误码"，但我的项目用的是自定义业务错误码体系。

**正确做法**：自己写，或者至少自己审阅修改。CLAUDE.md 的价值不在于格式多标准，而在于**它反映了你对项目的真实理解**。

可以让 Claude 帮忙生成初稿，但必须根据实际情况逐条调整。

---

## 反模式 5：写完不改

**表现**：项目初期的 CLAUDE.md 写好后，几个月不动。

**问题**：项目在演进，规范在变化。两个月前"所有 API 返回 JSON"的规则，现在可能改成"部分 API 返回 Protobuf"。过时的规则比没有规则更糟糕——它会误导 Claude。

**正确做法**：每隔一段时间（我大概一个月）回顾一下 CLAUDE.md，删掉不再适用的规则，补充新产生的约定。或者每次发现 Claude 做了不符合预期的事情，就把正确的规则补上去。

CLAUDE.md 是一个**活的文档**，不是一次性写完的。

---

## 反模式 6：规则应该由 Hook 或 Skill 执行

**表现**：在 CLAUDE.md 里写"每次提交前运行 hexo generate 检查构建是否通过"。

**问题**：CLAUDE.md 的规则靠 Claude 自觉遵守，但 Claude 不一定每次都记得。这种**必须执行的规则**应该用 Hook 来强制：

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "git commit",
      "command": "hexo generate"
    }]
  }
}
```

Hook 是硬约束，Claude 不可能跳过。CLAUDE.md 是软约束，靠"提醒"生效。

**正确做法**：

- **必须遵守的规则**（安全、构建验证、代码风格检查）→ 用 Hook
- **最好遵守的规则**（命名偏好、架构约定、注释风格）→ 写在 CLAUDE.md

---

## 反模式 7：规则太抽象

**表现**：

```markdown
- 保持代码整洁
- 写高质量的代码
- 遵循最佳实践
```

**问题**："整洁"和"高质量"对不同的人意味着完全不同的事情。Claude 可能认为"每个函数都加注释"是高质量，而你觉得注释应该只在必要时加。

**正确做法**：把抽象规则替换成具体操作：

```markdown
# 抽象 → 具体
"保持代码整洁" → "所有公共函数必须有 godoc 注释，私有函数不需要"
"写高质量代码" → "所有函数不超过 50 行，超过就拆分"
"遵循最佳实践" → "错误处理用 internal/errors 包的 Wrap 方法，不直接返回 error"
```

具体到 Claude 可以直接执行的程度，才是一条有效的规则。

## 健康的 CLAUDE.md 清单

用这个清单快速检查你的 CLAUDE.md：

- [ ] 总行数在 200 行以内
- [ ] 每条规则都写了"应该怎么做"，不只是"不要怎么做"
- [ ] 全局和项目的规则没有混淆
- [ ] 规则足够具体，Claude 可以直接执行
- [ ] 必须强制执行的规则已经迁移到 Hook
- [ ] 最近一个月内更新过

中了几条？不用追求全过，但至少保证前两条：**短**和**有方向**。一个好的 CLAUDE.md 不在于覆盖面多广，而在于每条规则都精准有用。
