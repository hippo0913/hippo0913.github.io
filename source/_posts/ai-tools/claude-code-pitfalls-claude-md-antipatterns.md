# 写好 CLAUDE.md 的 7 个反模式

CLAUDE.md 的内容每次对话都会加载到上下文窗口里。一个 700 行的 CLAUDE.md 大约占 8000-10000 token，而 Claude Code 的上下文窗口总共 200K token——看起来比例不大，但加上你的提问、代码文件、对话历史，这些空间消耗得很快。CLAUDE.md 写得越臃肿，留给实际工作的空间就越少。

这篇文章把我踩过的 7 个坑归成三组：规则怎么写、放在哪里、怎么维护。每组都有错误示例和修正方法，最后附一张速查表。

## 规则编写三原则：短、有方向、具体

7 个反模式里有三个都和"规则本身写得不好"有关：写得太长（反模式 1）、只禁不导（反模式 2）、太抽象（反模式 7）。归成三个原则来讲。

### 原则一：控制在 200 行以内

把项目里的所有规范、历史决策、架构说明全塞进 CLAUDE.md，看着很全面，但 Claude 每次对话都要读一遍这些内容。200 行以内的 CLAUDE.md 大约占 2000-3000 token，是一个合理的开销。超过 500 行就该考虑精简了。

项目背景、架构决策记录可以放在单独的文档里，CLAUDE.md 里提一句"架构决策见 docs/adr/"就够了。Claude 需要时会自己去找。

```markdown
# CLAUDE.md 推荐结构（约 100 行）

## 项目信息（5-10 行）
框架、语言、数据库、关键目录

## 代码规范（15-20 行）
命名、错误处理、日志等日常开发中最常用的约定

## 注意事项（5-10 行）
安全要求、不能做的事情

## 常用命令（5 行）
build、test、deploy
```

### 原则二：正面指令优于负面禁令

只写"不要做什么"的问题是：Claude 知道不能做 A，但它不知道该做 B 还是 C。比如"不要用 fmt.Println"，Claude 可能改用 log.Println，但你其实希望它用项目自定义的 logger。

每条禁令配上正确做法：

```markdown
# 错误：只有禁止
- 不要用 fmt.Println
- 不要硬编码
- 不要忽略错误

# 正确：禁止 + 方向
- 日志用 internal/logger，不要用 fmt.Println
- 密钥从环境变量读取，不要硬编码
- 所有错误必须显式处理并返回，不要用 _ 忽略
```

### 原则三：具体到可执行

"保持代码整洁"、"遵循最佳实践"这种规则对 Claude 来说等于没说。"整洁"和"高质量"对不同的人意味着完全不同的事情。Claude 可能认为每个函数都加 10 行注释是高质量，而你觉得注释应该只在必要时加。

把抽象规则替换成具体操作：

```markdown
# 抽象 → 具体
"保持代码整洁"       → "所有公共函数必须有 godoc 注释，私有函数不需要"
"写高质量代码"       → "所有函数不超过 50 行，超过就拆分"
"遵循最佳实践"       → "错误处理用 internal/errors 包的 Wrap 方法，不直接返回 error"
"注意安全性"         → "所有 SQL 查询使用参数化，禁止字符串拼接 SQL"
```

判断标准：Claude 看到这条规则后能不能直接执行，不需要猜。如果能，就是好规则。

## 职责边界：全局 vs 项目 vs Hook

反模式 3（全局 CLAUDE.md 写了项目规则）和反模式 6（该用 Hook 的写进 CLAUDE.md）本质上是同一个问题：规则放错了位置。

### 全局、项目、Hook 三层分工

| 配置层 | 文件位置 | 生效范围 | 适合放什么 | 举例 |
|--------|---------|---------|-----------|------|
| 全局 CLAUDE.md | ~/.claude/CLAUDE.md | 所有项目 | 通用工作习惯、语言偏好 | "回复用中文"、"优先用非交互命令" |
| 项目 CLAUDE.md | 项目根目录 CLAUDE.md | 当前项目 | 项目特有约定、目录结构、命名规范 | "API 用 Gin 框架"、"数据库用 PostgreSQL" |
| Hook | .claude/settings.json | 当前项目 | 必须强制执行的规则 | "提交前必须通过构建"、"禁止 rm -rf" |

一个常见的错误：在全局 CLAUDE.md 里写"数据库用 PostgreSQL"。结果切换到博客项目时，Claude 还在试图用 PostgreSQL 的约定。

### Hook 硬约束 vs CLAUDE.md 软约束

CLAUDE.md 的规则靠 Claude 自觉遵守，但 Claude 不一定每次都记得。"每次提交前运行 hexo generate 检查构建"这种必须执行的规则，应该用 Hook 强制。

Hook 的真实配置格式（`.claude/settings.json`）：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "git commit",
        "hooks": [
          {
            "type": "command",
            "command": "hexo generate"
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "notify.sh"
          }
        ]
      }
    ]
  }
}
```

简单判断：如果这条规则违反了会导致严重后果（构建失败、数据丢失、安全漏洞），就用 Hook。如果只是偏好和风格问题，写在 CLAUDE.md 就够了。

## 维护陷阱：生成不改与过时不更新

反模式 4（用 Claude 生成 CLAUDE.md）和反模式 5（写完不改）是一对：前者是起点错了，后者是终点懒了。

### 生成不改：起点就偏了

开一个空项目让 Claude "帮我写一份 CLAUDE.md"，拿到的通常是泛泛的标准规范——"遵循 Go 最佳实践"、"写好注释"、"使用标准错误码"。但我在 Go 后端项目里用的不是标准 HTTP 错误码，而是自定义的业务错误码体系。Claude 生成的 CLAUDE.md 完全没提这个。

CLAUDE.md 的价值不在于格式多标准，而在于它反映了你对项目的真实理解。可以让 Claude 帮忙生成初稿，但必须逐条审阅，把不符合实际情况的规则改掉。

### 过时不更新：规则变成误导

项目初期的 CLAUDE.md 写好后几个月不动，但项目在演进。"所有 API 返回 JSON"的规则，现在可能改成"部分 API 返回 Protobuf"。过时的规则比没有规则更糟糕——它会把 Claude 引向错误方向。

**什么时候该更新 CLAUDE.md：**

```markdown
# CLAUDE.md 更新触发时机
- 发现 Claude 的输出不符合预期 → 补充正确规则
- 项目引入新框架或新工具 → 添加相关约定
- 团队做了新的技术决策 → 更新对应规则，删除旧的
- 删除或重构了某个模块 → 清理相关规则
- 定期回顾（建议每月一次）→ 删除不再适用的规则
```

发现 Claude 行为异常时的操作流程：先看 CLAUDE.md 里有没有相关规则 → 没有，就加一条具体的 → 有了但还是不遵守，说明规则太抽象或该升级为 Hook。

## 速查表

| 反模式 | 表现 | 正确做法 | 配置位置 |
|--------|------|---------|---------|
| 大而全 | 700 行塞满所有规范 | 200 行以内，只写日常工作需要的 | 项目 CLAUDE.md |
| 只有不要 | 列一堆禁令没方向 | 每条禁令配上正确做法 | 项目 CLAUDE.md |
| 全局写项目规则 | ~/.claude/CLAUDE.md 写框架名 | 全局只放通用习惯，项目规则放项目目录 | 全局 vs 项目 |
| Claude 生成不改 | 直接用生成结果 | 逐条审阅，按实际情况修改 | 项目 CLAUDE.md |
| 写完不改 | 几个月不更新 | 每月回顾 + 遇到问题就补规则 | 项目 CLAUDE.md |
| 该 Hook 的写 CLAUDE.md | 提交前检查写在 CLAUDE.md | 必须执行的规则用 Hook 强制 | .claude/settings.json |
| 规则太抽象 | "遵循最佳实践" | 具体到可执行的操作指令 | 项目 CLAUDE.md |

**最小可用 CLAUDE.md 模板**（直接复制修改）：

```markdown
# 项目名

## 项目信息
- 框架/语言：
- 关键目录：

## 代码规范
- 命名风格：
- 错误处理：
- 日志工具：

## 禁止事项
- 不要 xxx，改用 yyy（每条都带方向）

## 常用命令
- 构建：
- 测试：
- 部署：
```

一个好的 CLAUDE.md 不在于覆盖面多广，而在于每条规则都精准、具体、可执行。先把这三点做到，其他的在维护中慢慢补。
