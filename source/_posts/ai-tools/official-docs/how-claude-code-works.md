# 精读官方文档：Claude Code 如何工作

> hippo：理解 Claude Code 的工作原理，能帮你预判它的行为、写出更有效的提示词、知道什么时候该信任它、什么时候要小心。

---

## 一、这个功能是什么

Claude Code 不是一个代码补全工具，而是一个**代理框架（Agentic Framework）**——它在 Claude 模型外面套了一层工具系统、上下文管理和执行环境，把语言模型变成了能真正动手编码的代理。

| 特性 | 代码补全 | 代理编码（Claude Code） |
|---|---|---|
| **触发方式** | 你打字它补全 | 你说目标它执行 |
| **输入范围** | 当前文件 | 整个代码库 + 历史对话 |
| **输出** | 代码片段 | 完整的任务执行结果 |
| **能力** | 写代码 | 读代码、写代码、跑命令、调试、搜索网络 |

> hippo：这个区别很关键——你给它**目标**，不是**步骤**。让 Claude 自己决定用什么工具、怎么组合。

## 二、官方教程精读

### 2.1 代理循环与工具系统

当你给 Claude 一个任务时，它经历三个阶段：**收集上下文 → 采取行动 → 验证结果**。三阶段循环往复，直到任务完成——你随时可以中断引导方向。

以"修复失败测试"为例，Claude 会自动跑完这个流程：

1. 运行测试套件，看哪些挂了（执行工具）
2. 读取错误输出，定位问题（搜索工具）
3. 搜索并读取相关源文件（文件操作工具）
4. 编辑文件修复问题（文件操作工具）
5. 再次运行测试验证（执行工具）

每一步的结果都反馈给下一步，这就是代理循环的实际运作。

**五大工具类别：**

| 类别 | 能做什么 |
|---|---|
| **文件操作** | 读取、编辑、创建、重命名文件 |
| **搜索** | 按模式查找文件、正则搜索内容、探索代码库 |
| **执行** | 运行 shell 命令、启动服务器、运行测试、使用 git |
| **网络** | 搜索网络、获取文档、查找错误消息 |
| **代码智能** | 类型错误检查、跳转定义、查找引用 |

在核心工具之上还有四个扩展层：**Skills**（自定义技能）、**MCP**（外部工具协议）、**Hooks**（生命周期钩子）、**Subagents**（子代理）。它们不改变底层循环，而是增强 Claude 的能力边界。

### 2.2 模型选择

Claude Code 使用 Claude 模型来理解代码和推理任务。多个模型可用，各有取舍：**Sonnet** 处理大多数编码任务表现良好，**Opus** 在复杂架构决策上提供更强的推理能力。

```bash
claude --model <name>    # 启动时指定模型
/model                   # 会话中切换模型
```

> hippo：日常用 Sonnet 就够了，遇到复杂重构或架构设计时切 Opus，性价比更高。

### 2.3 Claude 能访问什么

当你在某个目录运行 `claude` 时，Claude Code 获得以下访问权限：

- **你的项目**：当前目录及子目录的文件，经你许可后也可访问其他位置
- **你的终端**：所有你能在命令行执行的命令——构建工具、git、包管理器、系统工具、脚本
- **你的 git 状态**：当前分支、未提交的更改、最近的提交历史
- **你的 CLAUDE.md**：存储项目规则、约定和上下文的 Markdown 文件
- **自动记忆**：Claude 在工作中自动保存的学习内容（项目模式、你的偏好）。MEMORY.md 的前 200 行或 25KB（以先到者为准）在每个会话开始时加载
- **你配置的扩展**：MCP 服务器、Skills、Subagents、Claude in Chrome 等

> hippo：正因为 Claude 能看到整个项目，它才能跨文件协调编辑。这和只看当前文件的代码补全完全不同。

### 2.4 执行环境与界面

Claude Code 有三种执行环境，底层代理循环相同：

| 环境 | 代码运行位置 | 典型场景 |
|---|---|---|
| **本地** | 你的机器 | 默认模式，完全访问本地文件和工具 |
| **云** | Anthropic 管理的 VM | 处理本地没有的仓库、卸载任务 |
| **远程控制** | 你的机器，从浏览器控制 | 用 Web UI 操作，数据留在本地 |

界面方面，除了终端，还有桌面应用、IDE 扩展、claude.ai/code、Slack 集成、CI/CD 管道等。界面不同，代理循环不变。

### 2.5 会话管理与上下文窗口

**会话是独立的**：每个新会话以全新的上下文窗口开始，没有历史对话。跨会话持久化靠两样东西——**CLAUDE.md**（项目规则文件）和**自动记忆**（MEMORY.md 前 200 行或 25KB，以先到者为准，在会话开始时自动加载）。

```bash
# 会话恢复与分叉
claude --continue              # 恢复同 ID 会话
claude --resume                # 同上
claude --continue --fork-session  # 分叉为新 ID，保留历史但互不干扰

# 上下文管理
/context                       # 查看上下文占用
/compact                       # 手动压缩
/compact focus on the API changes  # 带焦点压缩，保留指定内容
/mcp                            # 查看 MCP server 的上下文成本
```

**跨分支工作：** 每个 Claude Code 对话是与当前目录绑定的会话。恢复时只能看到该目录的会话。Claude 看到的是当前分支的文件——切换分支后文件会变，但对话历史不变，Claude 仍然记得之前讨论的内容。

由于会话绑定目录，你可以用 **git worktrees**（为不同分支创建独立目录）来并行运行多个 Claude 会话。

> hippo：用 worktrees 做并行开发很实用——一个 worktree 让 Claude 写功能，另一个让它修 bug，互不干扰。

**上下文填满时的压缩策略**：Claude Code 在接近上下文限制时自动管理——优先清除旧工具输出（如长测试日志），然后总结对话早期内容，保留用户请求和关键代码。持久的规则应该放在 CLAUDE.md 中，而非依赖对话历史。

控制压缩保留内容的两种方式：
1. 在 CLAUDE.md 中添加 "Compact Instructions" 小节，指导压缩时保留什么
2. 运行 `/compact focus on ...` 带焦点压缩，如 `/compact focus on the API changes`

如果单个文件或工具输出过大，导致每次总结后上下文立即被重新填满，Claude Code 会在几次尝试后停止自动压缩并报错（thrashing error），避免无限循环。运行 `/context` 查看上下文占用，`/mcp` 查看 MCP 服务器的上下文成本。

**Skills vs Subagents 的上下文行为：**

| 机制 | 上下文行为 | 最佳实践 |
|---|---|---|
| **Skills** | 描述在会话开始时加载（约 100-500 tokens），内容按需加载 | 设置 `disable-model-invocation: true` 避免自动加载 |
| **Subagents** | 独立上下文窗口，不占主对话空间 | 用于大任务隔离（如重构整个模块） |

### 2.6 检查点与权限

**检查点**是 Claude Code 的"后悔药"：每次文件编辑前自动创建快照，按两次 Esc 即可回退上一个检查点。但要注意，检查点只覆盖本地文件，不覆盖 shell 命令、数据库操作或远程 API 调用。

**四种权限模式**（按 Shift+Tab 循环切换）：

| 模式 | 文件编辑 | Shell 命令 | 适用场景 |
|---|---|---|---|
| **默认** | 询问 | 询问 | 新手、敏感项目 |
| **自动接受编辑** | 自动 | 自动运行 mkdir、mv 等常见文件系统命令，其他仍需确认 | 日常开发 |
| **Plan Mode** | 禁止 | 禁止 | 复杂任务规划 |
| **自动模式** | 自动 | 自动 | 研究预览，高风险 |

```json
// .claude/settings.json - 允许特定命令免确认
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(git status)",
      "Bash(git diff)"
    ]
  }
}
```

```bash
# 命令行指定权限模式
claude --permission-mode plan      # Plan Mode
claude --permission-mode accept    # 自动接受编辑
claude --permission-mode default   # 默认
```

权限配置有三个作用域：组织级（`~/.claude/settings.json`） < 项目级（`.claude/settings.json`） < 命令行（`--permission-mode`），后者覆盖前者。

## 三、官方使用技巧

官方文档新增了一组实用技巧，以下是 hippo 认为最值得关注的要点：

### 3.1 对话式使用，不用追求完美提示词

Claude Code 是对话式的。你不需要完美的提示词——先说出你想要的，再迭代修正。第一次尝试不对？不用重来，直接说哪里不对，Claude 会调整。你也可以随时中断 Claude 的工作来纠正方向。

### 3.2 给 Claude 验证的依据

Claude 能检查自己的工作时表现更好。给它测试用例、贴期望 UI 的截图、或者定义期望输出。视觉工作尤其有效——贴一张设计图，让 Claude 对比自己的实现。

### 3.3 先探索再实现

复杂问题把研究和编码分开。用 Plan Mode（`Shift+Tab` 两次）先分析代码库，审查计划后再执行。这种两阶段方法比直接写代码效果好得多。

### 3.4 委托而非指挥

把它想象成委托给一个有能力的同事——给上下文和方向，信任 Claude 自己搞定细节。你不需要指定读哪些文件、跑什么命令，Claude 会自己判断。

## 四、hippo 的实战经验

> hippo：以下是我实际使用中踩过的坑和总结的建议：

### 4.1 上下文满了会翻车

我踩过最大的坑就是"让它一直做"。上下文满了之后，Claude 开始遗忘早期约束，输出质量明显下降。

**我的解法**：完成一个大功能后，主动 `/clear` 重启。重启前让 Claude 写个进度总结到 `.md` 文件，新 session 读这个文件继续。比硬撑着一直做效果好很多。

### 4.2 提示词精确度的差异

| 模糊提示 | 精确提示 |
|---|---|
| "优化代码" | "把这个 O(n²) 的排序改成 O(n log n)" |
| "修复 bug" | "修复 login.ts 第 42 行的 TypeError，缺少 undefined 检查" |
| "添加功能" | "在用户注册时发送欢迎邮件，复用现有的 mailer 服务" |

你的初始提示越精确，需要的纠正就越少。

### 4.3 先探索再实现，敏感操作要 Plan

复杂任务我习惯先用 Plan Mode 让 Claude 分析代码库、输出计划，审查后再执行。涉及生产配置、删除操作、数据库迁移时尤其重要——检查点只覆盖本地文件，远程操作不可逆。
